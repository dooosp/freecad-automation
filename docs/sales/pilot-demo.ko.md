# 99만 원 파일럿 데모 진행안

FreeCAD Automation | 고객 미팅용 | 2026-10-29

**15분 동안 확인할 것:** 입력 설정으로 실제 STEP/STL을 만들고, 품질 검사와 파일 근거를 확인한 뒤, 같은 작업을 다시 실행할 수 있는지 살펴봅니다. 공개 브래킷 예제로 진행합니다. 고객 부품의 성공, 작업 시간 절감 또는 제조 승인을 미리 약속하는 시연이 아닙니다.

15분은 설명 진행 시간입니다. 설치·다운로드는 미리 완료하며, 생성 시간은 컴퓨터와 런타임 상태에 따라 달라집니다. 실행이 늦어지면 실제 상태를 보여주고 생성 결과 확인 시간을 별도로 잡습니다.

## 미팅 전 준비

- 쓰기 권한이 있는 로컬 소스 체크아웃, Node.js 24 이상, FreeCAD 1.1.x가 설치된 macOS를 준비합니다. Windows/Linux는 별도 환경 검증 대상입니다.
- 저장소 루트에서 `npm ci`를 완료합니다. FreeCAD 설치 파일은 이 프로젝트에 포함되지 않습니다.
- 터미널과 브라우저만 화면 공유합니다. 고객 파일, 다른 프로젝트 경로, 알림을 노출하지 않습니다. 공개 예제 `configs/examples/quality_pass_bracket.toml`만 사용합니다.
- 아래 환경 확인과 생성 명령을 미리 리허설합니다. 사전 실행 결과를 보여줄 때는 실행 일시와 환경을 밝히고, 라이브 결과와 구분합니다.
- 소개 페이지와 PDF 제안서를 준비합니다. 고객의 상세 모델·치수·개인 연락처는 공개 GitHub 문의에 올리지 않습니다.

## 0:00-2:00 | 고객의 반복 작업과 파일럿 범위

**진행 멘트**

> “반복해서 만드는 부품군 하나를 골라, 합의한 입력에서 같은 방법으로 결과를 만들고 확인하는 흐름을 구축합니다. 오늘은 공개 샘플로 설치부터 산출물 확인까지 보여드립니다. 고객 부품은 별도 범위 확인과 검수를 거칩니다.”

고객에게 확인할 내용은 부품군의 일반적인 종류, 반복 빈도, 현재 작업 순서, 원하는 출력 형식입니다. 기밀 치수나 도면은 화면 공유·공개 문의에서 받지 않고, 전달 방법을 별도로 합의합니다.

**제안 조건:** 부가세 별도 **990,000원**, 회사 1곳, 합의한 실행 환경 1개, 부품군 1개, 파라미터 조합 **최대 10개**, 설정 수정 **2회**, 인계 후 **14일** 안에 총 **2시간** 원격 지원입니다. 지원은 고객이 요청하고 승인한 세션에서 진행합니다. 시작일·납기·결제 조건은 범위 확인 후 별도 확정하며, 14일은 납기 약속이 아닌 인계 후 지원 기간입니다.

## 2:00-4:00 | 환경 확인

저장소 루트의 터미널에서 실행합니다.

```bash
npm run customer:quickcheck
```

**화면에서 확인:** `Customer quickcheck: ready`, Node/FreeCAD 버전, 다음 명령 안내. `ready`는 런타임 준비 상태이며, 아직 CAD를 생성하지 않았습니다. JSON 출력에서 데모 상태는 `not_requested`입니다.

**진행 멘트**

> “실제 FreeCAD 런타임을 사용할 수 있는지 먼저 확인합니다. 환경 확인 성공과 모델 품질 통과는 서로 다른 단계입니다.”

`blocked`가 나오면 아래 실패 대응으로 이동합니다. 생성 성공 화면으로 넘어가지 않습니다.

## 4:00-8:00 | 실제 생성과 검수 근거

```bash
npm run customer:quickcheck -- --create-demo
```

이 명령은 공개 브래킷 설정을 새로운 `output/customer-demo/run-*` 폴더에 복사하고 출력 위치를 바꾼 뒤 기존 `create --strict-quality`를 실행합니다. 실행마다 새 폴더를 사용합니다.

**통과 시 확인:** `Customer quickcheck: demo_passed`와 `Demo verified:` 안내, 이번 실행의 `Output:` 경로. `demo_passed`가 아니면 통과로 설명하지 않습니다.

화면에 출력된 실제 경로로 파일을 엽니다. 예시 `run-*`를 그대로 파일 경로로 입력하지 않습니다.

| 파일/필드 | 고객에게 보여줄 근거 |
| --- | --- |
| `step`, `stl` | 실제로 생성된 비어 있지 않은 STEP/STL 파일 |
| `create_quality`의 `status` | `pass`, 차단 이슈가 없는지 확인 |
| `geometry.valid_shape` | `true`: 생성 형상의 유효성 검사 |
| `step_roundtrip.reimport_attempted`, `reimport_valid` | 모두 `true`: 내보낸 STEP을 실제로 다시 읽은 결과 |
| `stl_quality.mesh_load_attempted`, `watertight_or_closed` | 모두 `true`, `triangle_count > 0`: STL을 실제로 읽고 검사한 결과 |
| `output_manifest`, `artifact_manifest` | 입력·출력·명령·실행 근거와 현재 STEP/STL의 파일 크기·SHA-256 일치 확인 |

quickcheck는 위 조건과 기존 JSON 스키마를 확인한 후에만 `demo_passed`를 반환합니다. 생성 파일의 존재만으로 통과시키지 않습니다.

**진행 멘트**

> “결과 파일과 함께 어떤 입력으로 만들었는지, 실제로 다시 읽어 검사했는지 남깁니다. 이 결과는 이번 샘플의 소프트웨어 검수 근거이며, 실물 공차 검사나 제조 승인 자료는 아닙니다.”

## 8:00-11:00 | Studio에서 작업 이력과 산출물 확인

별도 터미널에서 서버를 실행한 뒤 안내된 주소를 엽니다.

```bash
npm run serve
```

기본 주소는 `http://127.0.0.1:3000/studio`입니다. 포트가 사용 중이면 기존 프로세스를 종료하지 말고 다른 포트를 지정합니다.

```bash
npm run serve -- 3318
```

이 경우 `http://127.0.0.1:3318/studio`를 엽니다. 브라우저 화면의 API 연결 상태와 런타임 준비 상태를 각각 확인합니다.

1. 콘솔에서 **검증된 브래킷 불러오기** / **Load verified bracket**을 누릅니다.
2. **먼저 추적 생성 실행** / **Run tracked create first**를 한 번 누릅니다.
3. 작업 센터에서 이번 작업 ID와 실행 상태를 확인합니다. 대기·실행 중이면 그대로 설명합니다.
4. 완료되면 패키지/산출물 화면에서 해당 작업의 파일을 확인합니다. 이전 작업이나 체크인된 예제 패키지를 이번 결과로 제시하지 않습니다.

**진행 멘트**

> “Studio는 작업과 산출물을 찾아가는 화면입니다. 여기의 작업 성공은 실행이 끝났다는 뜻입니다. 품질 근거가 없는 항목은 Quality/Ready가 Unknown일 수 있으며, 그 상태를 품질 통과로 바꾸어 설명하지 않습니다.”

CLI 데모는 Studio의 작업 이력에 자동 등록되지 않습니다. 지금 누른 추적 생성은 별도 작업입니다. CLI의 `demo_passed`와 Studio의 `succeeded`를 혼동하지 않습니다. 체크인된 canonical 패키지의 readiness 보류나 실물 검사 근거 부족도 이번 생성으로 해제되지 않습니다.

## 11:00-13:00 | 반복 실행과 인계 방법

다시 실행합니다.

```bash
npm run customer:quickcheck -- --create-demo
```

첫 실행과 다른 `Output:` 경로가 생기는지 확인합니다. 두 실행 모두 통과했는지, 첫 실행의 결과 파일이 남아 있는지 확인합니다. 두 실행의 출력 경로·상태·실행 시각을 기록합니다. 새 파일의 해시가 이전 실행과 같아야 한다고 약속하지 않습니다. 파일마다 해당 실행의 매니페스트와 일치해야 합니다.

**진행 멘트**

> “납품에는 결과 파일뿐 아니라 입력 설정, 재실행 명령, 검수 기록을 포함합니다. 고객이 같은 환경에서 다시 실행하고 문제가 생겼을 때 어느 단계에서 멈췄는지 확인할 수 있도록 인계합니다.”

생성이 13분 시점까지 완료되지 않으면 대기 상태를 기록하고 범위 설명으로 이동합니다. 끝나지 않은 재실행을 성공으로 기록하지 않습니다.

## 13:00-15:00 | 고객 파일럿 검수와 다음 단계

**검수 방식**

1. 계약 전에 부품군, 기존 지원 형상에 맞는 입력, 최대 10개 조합 목록과 실행 환경을 합의합니다.
2. 합의한 각 조합의 STEP/STL을 생성하고 strict create-quality, 실제 STEP 재읽기·STL 검사, 매니페스트 근거를 확인합니다. 실패·미실행 조합은 통과 목록에 넣지 않습니다.
3. 같은 설정의 별도 디렉터리 재실행, 입력·명령·검수 기록 인계와 고객의 재실행 확인을 기록합니다.
4. 기존 작업과 자동화 작업의 사람 투입 시간·전체 완료 시간을 구분해 측정합니다. 수정·재시도 시간을 포함하며, 절감 효과는 측정 후 판단합니다.

**진행 멘트**

> “99만 원은 무료 MIT 소스의 사용료가 아니라 설치·고객별 설정·검수·인계와 정해진 지원에 대한 제안입니다. 오늘 데모가 맞는 방향이라면 부품군과 조합 목록을 먼저 확정하고, 일정과 결제 조건을 제안서에 반영하겠습니다.”

복잡한 조립, 신규 형상 엔진, 클라우드 다중 사용자, Windows/Linux 전체 워크플로우 지원 보증, 무제한 수정·지원은 포함하지 않습니다. 도면·FEM·PDF 엔지니어링 보고서는 기본 파일럿에 자동 포함되지 않으며 필요한 경우 별도 범위를 정합니다. 고객용 제안서 PDF와 엔지니어링 검증 보고서는 서로 다른 문서입니다. 제조 승인, 실물 검사, 공차·안전성 인증을 대체하지 않습니다.

## 실패 시 진행표

| 관찰한 상태 | 진행자 행동 | 고객에게 설명할 내용 |
| --- | --- | --- |
| quickcheck `blocked` | `npm run check:runtime` 실행, 표시된 설치·경로 안내 적용 후 quickcheck 재실행 | “현재 환경에서 런타임 준비가 확인되지 않아 생성 검수로 넘어갈 수 없습니다.” |
| `demo_failed` 또는 명령 비정상 종료 | 해당 실행 폴더의 `create.stdout.log`, `create.stderr.log`와 `issues` 확인. 원인 조치 후 새 실행 | “이번 실행은 통과하지 못했습니다. 로그와 실패 조건을 남기고 조치 후 다시 검수합니다.” |
| Studio API 연결 실패 | 서버 터미널의 실제 포트와 브라우저 주소 확인. 준비된 다른 포트 사용 | “브라우저와 로컬 API의 연결 문제이며, FreeCAD 준비 상태와 별개로 확인합니다.” |
| Studio 런타임 미준비 | 콘솔 런타임 카드의 해결 안내 적용 후 상태 새로고침 | “화면 연결은 되었지만 생성에 필요한 런타임 준비가 아직 확인되지 않았습니다.” |
| Studio 작업 실패·취소·실행 중 | 작업 ID와 실제 상태 보존, 반복 클릭하지 않고 원인 확인 | “현재 작업 상태는 화면과 같습니다. 완료·검수 전에는 성공 산출물로 전달하지 않습니다.” |
| Studio `Quality Unknown` / `Ready Unknown` | 상태를 그대로 보이고 CLI strict 검수 근거와 구분 | “이 작업에는 해당 품질 판단 근거가 없습니다.” |
| 라이브 실행을 완료할 수 없음 | 성공 주장 없이 중단. 사전 리허설 근거가 있으면 실행 시각·환경을 밝히고 별도 설명 | “이 자료는 사전 실행 결과이며 오늘의 라이브 통과 결과는 아닙니다.” |

실패를 숨기려고 `--strict-quality`를 빼거나 JSON의 상태를 수정하지 않습니다. 원시 로그는 로컬에서 확인하며, 공개 문의에 그대로 첨부하지 않습니다.

## 리허설 기록용 명령과 체크리스트

아래는 운영자가 JSON 근거를 별도 파일에 남길 때 사용하는 선택 절차입니다. 저장소 루트에서 실행합니다. 새 기록 폴더를 만들고 npm 배너가 없는 직접 CLI 진입점을 사용합니다.

```bash
mkdir -p output
PILOT_SESSION="$(mktemp -d "$PWD/output/pilot-demo-session.XXXXXX")"
node scripts/customer-quickcheck.js --create-demo --json > "$PILOT_SESSION/quickcheck.json"
PILOT_EXIT_CODE=$?
cat "$PILOT_SESSION/quickcheck.json"
printf 'Exit code: %s\n' "$PILOT_EXIT_CODE"
```

`PILOT_EXIT_CODE`가 `0`이고 JSON의 `status`가 `demo_passed`, `demo.status`가 `passed`인지 확인합니다. 실제 CAD 산출물은 JSON의 `demo.output_dir`에 있고, 위 폴더는 기록용 JSON 보관 위치입니다. 이 JSON이 있어도 상태가 `blocked`나 `demo_failed`면 통과 기록이 아닙니다.

| 기록 항목 | 작성할 내용 |
| --- | --- |
| 실행 일시·환경 | 실제 일시, OS, Node/FreeCAD 버전, 소스 커밋 |
| 첫 번째 실행 | 종료 코드, 상태, 출력 폴더, 품질/매니페스트 경로 |
| 두 번째 실행 | 같은 항목, 별도 출력 폴더 여부, 첫 결과 보존 여부 |
| Studio 실행 | 사용 포트, 작업 ID, 실제 작업/Quality/Ready 상태 |
| 실패·제한 | 실패·미실행 항목과 조치 내용, 라이브/사전 실행 구분 |
| 고객 파일럿 | 별도 합의할 부품군·조합 수·환경·납기·결제 조건 |

기록 파일은 기본적으로 로컬에 보관합니다. 공유 전 내용과 경로를 검토합니다. quickcheck는 결과나 로그를 자동 업로드하지 않습니다.
