# Inspection Plan and Supplier Checksheet

## Goal

Add one deterministic `fcad inspection-plan` workflow that converts explicit,
supported review-package requirements and revision-impact reinspection work into
one canonical `inspection_plan.json`. A supplier checksheet, supplier request,
and blank result template are derived only from the validated plan. The workflow
never creates results, evidence, authorization, readiness, or release state.

## Architecture before

`generate-standard-docs` renders `inspection_checksheet_draft.csv` from
heuristic readiness/report context. That draft is planning advice: it lacks a
field-level authority contract, stable plan-item identity, revision-impact
linkage, and a release boundary. Review packs carry explicit inspection
requirements; revision-impact reports carry exact changes and future
reinspection work; quarantine-first onboarding accepts externally completed
candidates only after validation and separate authorization.

## Architecture after

```text
review_pack + optional revision_impact/readiness/config/requirements
  -> bounded one-read snapshots and hashes
  -> inspection-plan authority/normalization policy
  -> canonical inspection_plan.json (structural + semantic validation)
  -> CSV/Markdown/blank CSV renderers using only canonical JSON
  -> atomic publication and artifact registration
  -> CLI / tracked job / Local API / existing Review-Packs Studio surface
```

Domain code belongs under `src/services/inspection-plan/`. CLI, jobs, API, and
Studio consume the same service and command metadata. No generic utility module
or second manifest system is introduced.

## Authority hierarchy

Closed levels are `authoritative_released_requirement`,
`explicit_review_requirement`, `revision_impact_requirement`,
`advisory_generated_context`, and `unresolved`. Authority is recorded per
field. Review-pack records whose role is an explicit inspection requirement and
stable drawing-intent characteristics may provide requirements. DFM, quality
risk, process suggestions, CAD geometry, standard-document drafts, QIF-lite
control XML, runtime fingerprints, and evidence graphs remain advisory.

Missing tolerance, method, equipment, sampling, revision, stable identity, or
conflicting values are never guessed. They remain null/unresolved and require
human review. A revision-impact requirement can create a delta item while its
method remains unresolved.

## Canonical contract

`schemas/inspection_plan.schema.json` defines artifact/schema identity, fixed
status and scope sets, package identity, source snapshots and SHA-256 values,
authority counts, stable items, unresolved requirements, derived-output
descriptors, and immutable safety boundaries. IDs are hashes of package,
revision, characteristic, and semantic source identity; timestamps, randomness,
and array position are excluded.

Every item starts `not_started`, has no measured result, and records that the
evidence state did not change. The only positive terminal planning status is
`ready_for_human_release`; automatic `released`, production approval, pass, or
supplier approval states are unsupported.

## Full and delta rules

Full scope includes every supported stable explicit requirement. Delta requires
a matching revision-impact report and includes exact linked
`reinspection_required`, affected `review_required`, and blocking
`unable_to_determine` work. Unaffected characteristics are not invalidated.

## Derived documents

The checksheet has a fixed documented UTF-8/LF/RFC-CSV column order, stable item
ordering, typed formula-injection protection, separate required/suggested
fields, and blank actual/result fields. The supplier request identifies the
plan/checksum, requirements, unresolved questions, required completion fields,
privacy guidance, and quarantine-first return path. The result template keeps
stable IDs and onboarding columns but contains no identity, measurements,
review, authorization, or PASS/FAIL claims. Its exact generated bytes remain
control material and cannot satisfy evidence onboarding.

## Safety, privacy, and determinism

Inputs are bounded UTF-8 JSON with duplicate-key, BOM, nesting, size, finite
number, path, URL, and secret checks. Each input is read once and the same
in-memory bytes/hashes feed all outputs and manifest metadata. Outputs are
restricted to ignored approved roots, one directory, and revision-impact-style
preflight/publication checks (traversal, NUL, symlink, hardlink, inode change,
locking, rollback/recovery). Fixed inputs plus `--generated-at` produce
byte-identical JSON, CSV, Markdown, template, and provenance hashes.

## Integration and rollout

Add one `inspection-plan` command and one same-named tracked job. The server
chooses the job artifact directory and accepts allowlisted registered input
artifacts. Existing Review/Packs UI provides selection, scope, run, summary,
preview, and reopen actions with English/Korean labels. It provides no approve,
release, attach, or mark-ready action.

Rollback removes this additive command/job/viewer and schema; no canonical
package migration is needed. Unsupported in v1: inferred CAD tolerances or
methods, generalized QIF, automatic release, supplier-data ingestion, evidence
attachment, private remote sources, and FreeCAD-backed measurement claims.
